# 코드 재사용과 공통 패키지 분리 기준

[재사용 원칙 Discussion](https://github.com/blahaj94/ldb/discussions/257)의 후속 합의를 [Issue #258](https://github.com/blahaj94/ldb/issues/258)에서 구체화하고 [PR #259의 사용자 승인](https://github.com/blahaj94/ldb/pull/259#issuecomment-5609921277)을 반영한 active Rule입니다. 승인된 변경을 반영한 checkout에서 적용합니다.

재사용 탐색, 자체 구현 판단, 공통 package 분리와 선택 근거의 관리는 이 문서를 따릅니다. 새 dependency, architecture와 보안 계약의 변경은 [기존 승인 절차](change-control.md#approval-evidence)를 유지합니다. 특정 라이브러리 선정, package 생성이나 기존 코드 교정을 일괄 승인하지 않습니다.

## 역할로 판단하기

- 사용 횟수는 재사용 검토나 공통화의 필요조건도 충분조건도 아닙니다. 한 곳에서만 쓰더라도 URL 파싱, 프로토콜 처리, 범용 재시도 등은 재사용 검토 대상입니다. 여러 곳에서 쓰이더라도 책임과 변경 이유가 다르면 억지로 합치지 않습니다.
- 표준 API나 라이브러리가 맡을 범용 기능과 프로젝트가 결정할 정책을 구분합니다. URL을 파싱하는 기능과 서비스에서 허용할 URL을 정하는 정책은 서로 다른 책임입니다. 프로젝트 고유의 정책도 공유할 독립 책임이 될 수 있습니다.
- 코드 길이, 함수 이름, 호출 횟수와 dependency 개수만으로 자체 구현이나 공통화를 정당화하지 않습니다. "몇 줄 안 된다", "단순 helper다", "dependency를 늘리지 않는다"는 이유만으로 재사용 검토를 생략하지 않습니다.
- 재사용할 구현을 고르는 판단, 소유 모듈을 정하는 판단과 새 package를 만드는 판단을 구분합니다. 공통 모듈로 옮겼다는 사실은 자체 구현을 선택한 근거가 아닙니다.

## 구현 전 재사용 탐색

공통 로직을 작성하거나 확장하기 전에 필요한 입력, 출력, 실패 조건과 실행 환경을 확인하고 다음 순서로 적합한 기능을 찾습니다. 작업 도중 범용 기능의 재구현이 필요하다는 사실을 발견하면 해당 구현을 더 늘리기 전에 같은 절차를 진행합니다.

1. 프로젝트의 기존 구현과 관련 결정 기록을 확인합니다. 같은 책임의 중복을 만들지 않되, 기존 코드가 있다는 사실만으로 선택을 정당화하지 않습니다. 계약이나 선택 이유가 불분명하면 그 사실을 드러냅니다.
2. Node.js, 브라우저 등 대상 런타임의 표준 API와 내장 모듈을 확인합니다. 이를 사용하는 것은 재사용이며 자체 재구현으로 분류하지 않습니다.
3. 이미 설치된 패키지에서 해당 계약을 제공하는지 확인합니다. 설치 여부만으로 요구 적합성이나 새로운 역할의 사용 승인을 추정하지 않습니다.
4. 적합한 기능이 없으면 유지보수되는 외부 오픈소스 후보를 검색하고 검토합니다. 요구 적합성, 지원 환경, 문서와 테스트, 유지보수 상태, 보안 대응 이력, 라이선스와 의존성 부담을 필요한 범위에서 확인합니다. 인기도나 최근 commit 수만으로 검증됐다고 판정하지 않습니다.

단순 adapter라는 예외는 입력 변환이나 프로젝트 정책 연결을 뜻합니다. 그 안에 범용 파싱, 재시도, 프로토콜 또는 경합 처리를 새로 구현하면 해당 책임에 대해 위 탐색과 아래 선택 절차를 적용합니다. 기존 Rule이나 계약과 충돌하는 선택은 임의로 진행하지 않습니다.

## 자체 구현과 유지보수 책임

- 적합한 기존 기능이나 후보가 없어 직접 구현을 선택하려면 구현 전에 검토한 후보, 요구를 충족하지 못한 구체적인 이유, 직접 보장할 범위와 유지보수 책임을 제시합니다. 라이브러리의 불확실성은 후보를 검토할 이유이며, 설명 없이 자체 구현으로 전환할 근거가 아닙니다.
- 비교에는 작성뿐 아니라 테스트, mock, 문서화, 리뷰, 변경 검증, 선택 배경의 재확인과 장애 원인 추적 비용을 포함합니다. 외부 라이브러리 도입 후에도 프로젝트가 맡을 통합, 업데이트와 제품 정책의 책임을 함께 설명합니다. 정밀한 비용 추정이나 포괄적인 후보 조사를 의무화하지 않습니다.
- 범용 기능의 최초 자체 구현 결정은 추천안과 실질적인 대안 1개, 각각의 trade-off를 짧게 제시하고 구현 전에 사용자 선택을 받습니다. Worker는 Planner에게 근거를 전달하고 선택에 영향받는 구현을 보류합니다. 결정이 필요 없는 독립 작업은 계속할 수 있습니다.
- 기존 결정은 [선택 근거의 기록과 재사용](#선택-근거의-기록과-재사용) 조건을 충족하면 참조합니다. 유효한 기존 승인을 반복 요청하지 않으며, 새 승인 경계를 기존 결정에 포함된 것으로 간주하지 않습니다.
- 새 dependency의 사전 승인은 사용 금지나 자체 구현 우선 지시가 아닙니다. 승인 절차를 피하려고 범용 기능을 직접 구현하지 않습니다. Planner가 dependency 추가를 제외하면 사용자 지시, 승인된 Rule이나 작업 범위의 근거를 Issue에 명시하고 필요한 후보 검토를 생략하지 않습니다.
- 승인된 자체 구현은 해당 책임의 소유 모듈에 모아 스펙, 선택 이유와 테스트를 함께 관리합니다. 지원 입력, 결과, 실패 조건, 필요한 동시성 보장과 지원하지 않는 범위를 드러냅니다. 테스트의 계층과 추가 필요성은 [testing.md](testing.md)를 따르며 사용 횟수만으로 새 테스트를 반복하지 않습니다.
- 외부 기능을 호출 그대로 전달하는 wrapper는 만들지 않습니다. 프로젝트의 공통 정책이나 실제 경계를 제공할 때 최소한으로 연결하며, 라이브러리의 일반 기능을 자체 API로 다시 구성하지 않습니다.

## 앱 내부 모듈과 공통 패키지

같은 책임은 먼저 그 책임을 소유한 모듈에서 관리합니다. 새 공통 package로 분리하려면 다음 조건을 모두 설명할 수 있어야 합니다.

1. **독립 책임과 계약:** 특정 화면이나 앱의 실행 흐름을 설명하지 않고도 제공 기능, 입력, 출력과 보장 범위를 말할 수 있습니다.
2. **앱으로 되돌아가지 않는 의존성:** 앱이 package를 사용하고 package는 소비 앱의 source나 전역 상태를 import하지 않습니다. 필요한 설정과 동작은 명시적인 입력으로 받습니다. 앱의 세부 사항을 대량으로 주입하거나 앱 종류별 분기가 계속 늘면 책임 경계를 다시 검토합니다.
3. **구체적인 경계 이점:** 앱 내부 모듈로는 충분히 확보하기 어려운 이점이 있습니다. 여러 소비자의 동일 계약 유지, 허용 의존성이나 실행 환경의 독립적인 제한, 공개 API를 통한 내부 구현 접근 제한 등이 해당할 수 있습니다. 별도 설정, 공개 API와 호환성, 빌드 및 테스트 관리 비용을 포함해 판단합니다.

소비자가 하나여도 세 조건을 충족하면 분리를 검토할 수 있습니다. 소비자가 많다는 사실, 코드의 유사성, 미래의 재사용 가능성이나 테스트 편의성만으로 package를 만들지 않습니다. 앱 내부 모듈로 충분하면 그 범위에서 관리합니다.

여러 앱의 비슷한 코드는 한쪽 요구가 바뀔 때 다른 쪽도 같은 이유로 바뀌어야 하는지 확인합니다. 같은 계약이나 정책을 유지해야 한다면 공유할 근거가 됩니다. 서로 다른 이유로 바뀌는 책임을 옵션과 분기로 억지로 합치지 않습니다.

| 상황 | 판단 |
| --- | --- |
| 한 앱의 여러 화면이 같은 화면 이동 도우미를 사용합니다. | 해당 앱 내부 공통 모듈로 충분한지 먼저 확인합니다. |
| Web과 Desktop이 같은 API 계약을 따라야 합니다. | 계약이나 클라이언트 package를 검토할 근거가 있습니다. 앱별 상태와 화면 이동은 각 앱이 소유합니다. |
| 여러 앱이 같은 라이브러리를 단순 호출합니다. | 각 앱에서 직접 사용할 수 있습니다. 내부 wrapper package는 별도의 책임이나 경계 이점이 필요합니다. |
| 소비자는 하나지만 실행 환경이나 의존성 제한을 독립적으로 강제해야 합니다. | 독립 계약과 의존성 방향을 포함한 세 조건을 만족하면 분리를 검토할 수 있습니다. |
| 구현 모양은 비슷하지만 앱마다 다른 이유로 변경됩니다. | 동일한 정책으로 합치지 않고 각 책임을 유지합니다. |

분리 제안에는 책임, 공개 계약, 의존성 방향과 앱 내부에 둘 때의 문제를 짧게 남깁니다. 실제 package 종류와 의존성 방향은 [architecture 승인 경계](../architecture/overview.md#architecture-change)를 따릅니다. 이 판단 기준이 개별 package의 생성 승인을 대신하지 않습니다.

## 선택 근거의 기록과 재사용

- 요구사항, 검토한 선택지와 선택 이유, 직접 책임질 범위, 적용 환경, 승인 근거와 재검토 조건을 한 결정 기록에서 확인할 수 있게 합니다. 기존 기록이 있으면 연결하고 매 PR마다 비교 문서를 새로 만들지 않습니다.
- 의도한 행동과 제약은 canonical Rule에, 현재 선택과 소유 모듈의 계약, 테스트 위치는 관련 Reference나 모듈 문서에 둡니다. 결정 과정과 승인 이력은 원래 Issue와 PR을 연결하며 원문을 여러 문서에 복제하지 않습니다. 파일 이름과 위치는 기존 문서 구조에 맞추고 일률적인 새 파일을 요구하지 않습니다.
- 후속 작업은 요구사항, 실행 환경, 사용 역할과 승인 범위가 같은지 확인한 뒤 기존 결정을 참조합니다. 새 선택이 필요하지 않으면 동일한 조사와 승인을 반복하지 않습니다.
- 지원 범위를 벗어난 입력이나 실패 조건, 실행 환경과 의존성 역할의 변화, 보장에 영향을 주는 버전 변경, 유지보수 중단이나 관련 보안 문제, 앱별 정책의 분기가 생기면 영향받는 판단을 재검토합니다. 기존 코드가 있다는 사실만으로 재사용을 강제하거나 전체 조사를 반복하지 않습니다.
- 결정이 바뀌면 현재 계약을 갱신하고 이전 근거를 연결해 무엇이 달라졌는지 확인할 수 있게 합니다. 새 dependency나 Rule, architecture와 보안 계약에 영향을 주면 해당 승인 절차를 유지합니다.

## 코드 리뷰

리뷰에서는 동작의 정확성과 함께 프로젝트가 그 코드를 직접 관리해야 하는 이유를 확인합니다.

- 기존 구현, 표준 API, 설치된 패키지와 필요한 외부 후보를 확인했거나 유효한 기존 결정을 참조했는지 확인합니다.
- 직접 구현한 범용 기능에는 선택 근거, 필요한 승인과 보장 범위를 검증하는 테스트가 있는지 확인합니다. 테스트 통과만으로 구현 선택의 타당성을 대신하지 않습니다.
- 같은 책임의 중복과 서로 다른 책임의 강제 공통화가 없는지 확인합니다. 새 package에는 독립 책임과 계약, 의존성 방향과 경계 이점의 근거가 있어야 합니다.
- 다음 작업자가 선택 이유와 스펙, 테스트를 찾을 수 있는지 확인합니다. 근거의 누락을 형식적인 비교 문서나 호출 횟수 기준으로 대신하지 않습니다.
